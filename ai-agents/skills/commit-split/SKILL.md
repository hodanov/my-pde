# /commit-split スキル

## Goal

未コミットの作業ツリーに混在した差分を、変更理由ごとのコミットへ分割する。

1 セッションの作業で機能追加・付随リファクタ・設定/ドキュメント修正が 1 コミットに固まると、レビュー側が毎回「どこが本題か」を切り分けることになり、部分 revert もできない。分割の単位は変更意図の判断が要るため、案を会話上で提示して確定してから手を動かす。

## Workflow

### Step 1: 差分を確定する

- `git status --short` で変更ファイルと未追跡ファイルを把握する
- `git diff` と `git diff --cached` で中身まで読む（既にステージ済みの内容を見落とさない）
- 差分が無ければ中断して報告する
- マージやコンフリクト解消の途中（`git status` に `UU`）なら、先に解消してから始める

### Step 2: 分割案を提示して承認を得る

- 差分を「変更理由」で分類する。同じ理由で同時に変わるものを 1 コミットに束ねる
- 各コミットについて type / 対象パス / 要約を列挙し、順序とあわせて提示する
- 既定は 2〜4 コミット。それを超える場合は理由を添える
- 1 つの変更理由にしかならないと判断したら、分割せずその旨を報告して `commit-and-draft-pr` へ渡す

### Step 3: 承認順にステージする

- ファイル単位で分かれるなら `git add <pathspec>`、1 ファイル内で理由が混ざるなら `git add -p` を使う
- ステージ後に `git diff --cached` を読み、そのコミットの意図と一致することを確認する
- 一時/デバッグ用ファイル、ローカル設定、秘密情報（`.env` 等）、生成物は原則除外する

### Step 4: コミット単独での成立を確認する

- そのコミットの変更ファイルに対応するテスト・リンタ・型チェックを実行する
- ハンク単位で分割した場合は中間コミットがビルド不能になりやすいため、この確認を飛ばさない
- 通らなければ束ね方を見直す（必要なハンクを同じコミットへ寄せる）

### Step 5: コミットする

- メッセージ形式・type 一覧・本文の書き方は `commit-and-draft-pr` の規約に従う
- Step 2 の分割案を 1 コミットずつ消化し、残り差分が無くなるまで Step 3 へ戻る

### Step 6: push と PR を委譲する

- 全コミットが揃ったら `commit-and-draft-pr` へ渡し、ブランチ確認・push・ドラフト PR 作成はそちらで行う

## Notes

- 対象は未コミットの作業ツリーのみ。push 済み履歴の書き換え（rebase / amend / force-push）には踏み込まない
- 中断するときは `git reset` でステージを戻し、作業ツリーを開始時の状態に保つ。半端なステージを index に残さない
- 分割しすぎるとレビュー負荷が逆に上がる。「別々に revert したいか」で単位を決める
- 承認前に `git add` しない。分割案はユーザーが確定するもので、こちらが先に index を作ると見直しが手戻りになる
