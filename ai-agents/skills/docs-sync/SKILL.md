# /docs-sync スキル

## Goal

実装の変更差分に追随してドキュメントを更新し、消えたフラグ・旧名・古い既定値が残ったまま次の読み手（人間と AI）が古い前提で作業するのを防ぐ。

`lint-changed`（Stop フック）は構文とスタイルしか見ず、文面として古いだけの記述は素通りする。`/review`・`/review-scan` は差分そのものの妥当性を見る観点なので、差分に現れない既存ドキュメントの取り残しは対象外。その隙間を埋める。

## Workflow

### Step 1: 差分を確定する

- 引数が base ブランチなら `git diff --name-only <base>...HEAD`、PR 番号なら `gh pr diff <番号> --name-only` で変更ファイルを取る
- 引数が無ければ既定のベースブランチ（`origin/HEAD` → `origin/main` → `origin/master` の順）との三点 diff を使う
- 差分が無ければ中断して報告する

### Step 2: 外部契約の語を抽出する

差分の中身を読み、呼び出し側が依存する語だけを抜く。

- 公開シンボル（関数・型・定数の名前）
- CLI のサブコマンドとフラグ
- 設定キー、環境変数、既定値
- ファイルパス、タスク名

実装内部のローカル変数やコメントは対象にしない。

### Step 3: 追随が必要な箇所を列挙する

- 抽出語を README / `docs/` / AGENTS.md / SKILL.md へ grep する（探索範囲はこの 4 種に固定する）
- ヒットした箇所を「ファイル:行」と現在の記述で列挙する
- ヒットが 0 件、または一般名詞で過多になった場合は書き換えず、列挙だけして止める

### Step 4: 該当箇所だけを更新する

- Step 3 で列挙した箇所に限定して書き換える。差分と無関係な文面は触らない
- 載っているコード例とコマンドは実際に実行して、出力が記述と一致することを確かめる
- 更新不要と判断した箇所は、理由を 1 行で報告する

### Step 5: 検証して委譲する

- `verify-changed`（リポジトリにあれば）または対応する Markdown リンタを走らせる
- コミット・push・PR は `commit-and-draft-pr` へ渡す

## Notes

- 網羅を狙わない。対象は Step 2 の抽出語にヒットした箇所だけに限定する。差分と無関係な文面まで書き換えると、レビューで本題が埋もれる
- 抽出語が一般名詞（`config`、`run`、`path` 等）のときはヒットが膨らむ。絞り込めないなら書き換えず列挙に留める
- 差分が大きいほど読むドキュメントが増えるため、探索範囲は Step 3 の 4 種に固定する
- ドキュメントの構成変更や新規ドキュメントの起案には踏み込まない。既存記述の追随だけを担う
