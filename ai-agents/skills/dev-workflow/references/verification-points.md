# 検証点の作り方（テストハーネスが無い領域）

lint が全部通っても、実行時にしか出ない不具合は残る。GUI オーバーレイやエディタ UI のように「手で押さないと確認できない」経路に当たったとき、**「確認できないので完了」で終わらせず、CLI から出力を取り出せる検証点を作る**ための手法カタログ。

## 手法（優先順）

### 1. 依存モジュールをスタブして素の処理系で実行する

本体を変更せずに済むので第一候補。設定ファイルが依存する API（`wezterm` 等）を偽実装して `package.preload` に差し込み、設定ファイルを `luajit` / `node` で直接実行する。登録されたコールバックをその場で呼べるので、GUI を起動せずに戻り値を検査できる。

さらに **スタブ側に本物の副作用を再現させる**と、状態遷移まで検証できる。偽ペインの `send_text` に「Ctrl-C を受けたら user var を `0` に落とす」を仕込む、`perform_action(SplitPane)` を受けたら偽タブにペインを足す、といった具合。これにより「操作の前後で結局どのタブに何本あるか」まで CLI から確認でき、`is_focused` ガード漏れによる毎秒 ping-pong や、死にかけペインを現役と誤認する race のような **GUI では再現待ちになる不具合を先に潰せる**。

### 2. 実装に小さな CLI 契約を用意する

`--once` / `--json` のようなサブモードを実装側に足し、GUI を経由せず同じロジックを走らせる。**implement の時点で用意しておく**のがコツで、後付けにすると検証のためだけの改修になって腰が重くなる。

「手で押さないと確認できない部分」と「CLI から確認できる部分」を先に切り分け、後者を最大化する設計にしておく。

### 3. 合成入力を食わせる

`ps` / `git` 等の出力を手で組み立てて判定ロジックに与え、真偽の両ケースを確認する。**誤検知（false positive）は本番環境では再現しにくい**ので、この手法でしか潰せないことが多い。

### 4. どれも取れない場合

「**未検証である**」ことと、未消化の手動確認項目をユーザー報告に明示する。プランドキュメントのチェックリストに残すのも有効。原因を特定できないまま対処に進んだ場合も、その旨を同様に明示する。

## 実行検証のチェックポイント

「動かした」で満足せず、**出力そのものを読み返す**。

- `cat -A` でタブ / スペース / 行末を**バイト列として**確認する（整形ツールの設定差はここでしか見えない）。
- CLI 側で同じ処理を走らせた結果と突き合わせる（エディタ統合と CLI で引数が違うことがある）。
- 生成した JSON / 設定ファイルを目視する。スキーマが通ることと意図どおりであることは別。
- 「黙ってスキップするはず」という前提は疑う。ログに `ENOENT` 等が出ていないか実際のログを読む。

## 領域別の具体パターン

| 対象                     | パターン                                                                                                                    |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Dockerfile               | `docker build --target <stage>` で修正対象ステージだけ先に単体ビルドし、数十秒で fix の正しさを確認してから全体ビルドを回す |
| 長時間ビルド             | ログを `\| tail -N` に通さない。`tee` でファイルに落とす（バックグラウンド実行時に進捗が一切読めなくなる）                  |
| 稼働中プロセスに触る変更 | まず使い捨て環境（`docker run --rm`）で確認し、本番反映（コンテナ再作成等）はユーザーの同意を取ってから                     |
| 課金の伴う E2E           | 外部呼び出しをスタブしてドライランで結線だけ通す。実課金の確認はユーザーに委ね、PR の確認事項に残す                         |

## 検証の永続性

- **検証スクリプトを scratchpad にだけ置かない**。session-specific な scratchpad は日を跨ぐと消える。リポジトリ内か永続パスに置くか、**検証手順そのものをコミットメッセージ / PR 本文に残す**。
- 日を跨いでから commit フェーズに入る場合、`main` の進行・依存の更新・スクリプトの消失がありうるので再検証する。「当セッション」でも「直後」でなければ再実行する。

## プラン記載の実測値

プランに実測値や手計算値が書かれている場合、**その再現を verify の一項目として扱う**。

ゴールデンテストは「今の実装の出力」を固定するだけで、**それが正しい定義かは保証しない**。順序は「定義を実データで確定 → 手計算値と照合 → テストで固定」であり、test_first とは逆になる。先にテストを書くと間違った期待値を固定してしまう。
