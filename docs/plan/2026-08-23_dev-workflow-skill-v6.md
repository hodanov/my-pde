## Design policy

### 重い手順は `references/` へ逃がす

このリポジトリには既に progressive disclosure の慣習がある（`credential-leak-prevention` / `permission-prompt-tuner` / `supply-chain-hardening` の 3 スキルが `references/*.md` を持ち、本文からは `詳細は [references/x.md](references/x.md) を参照` の 1 行で繋ぐ）。これに乗せ、判断の分岐点だけを SKILL.md に置き、手法カタログは参照先に置く。

配布経路は問題なし。`ai-agents/scripts/copy-entries.sh` の skills モードは `cp -R "$entry" "$target"` でディレクトリ丸ごとコピーするため、`references/` はそのまま `~/.claude/skills/` 側へ乗る。

### 既存スキルと重複させない

観測 `08-06_001` は「依存/lockfile 更新は new / existing / テストの無いタスクのどれでもない第三のカテゴリ」と指摘しているが、リポジトリには既に **`dependency-update` スキル**（v1）がある。dev-workflow 側に手順を書き写すのではなく **1 行のポインタだけ** 置く。

`08-06_001` の中身（verify を「バージョン番号の確認」で終わらせず ①脆弱性スキャン ②`npm ls` の実解決先 ③そのツール自体を動かす、の 3 段にする）は `dependency-update` 側の verify 節に足すほうが筋が良い。**今回のスコープ外** とし、フォローアップに回す。

### 「未検証」を敗北ではなく成果物にする

`08-21_001` の partial は「確認できないまま完了報告した」ことではなく、**確認できないことを構造的に解消できなかった** ことが問題だった（報告自体は明示していた）。v6 では検証点を作る手段を 3 つ提示したうえで、**どれも取れない場合は「未検証である」ことと未消化の手動確認項目を明示する** ところまでをフローの正規の終端として書く。これは `08-19_001` / `08-19_002` / `08-21_002` / `08-21_003` が実際にやっている運用の追認でもある。

## 検証

このタスク自体が「テストの無いタスク（ドキュメント）」なので、v6 で追記する規律を自分に適用する（dogfooding）。

1. **静的検証（変更ファイルにスコープ）** — 新ルール「リポジトリ全体を舐める verify は作業ツリーの差分に汚染される」の実践。作業ツリーには無関係な未追跡ファイル（`docs/worktrees.md`、`docs/svleague-match-review/`、`ai-agents/skills/trip-*`）があり、`mise run lint:format` をそのまま回すと落ちる。`markdownlint-cli2` と `prettier --check` を変更 6 ファイルにスコープして実行する。リポジトリルートから実行する（サブディレクトリへ `cd` すると markdownlint-cli2 が設定を見失い MD013 を誤検出する）。
2. **ベースライン差分** — 新ルールの実践。全体実行で残る指摘が変更前（HEAD）と同一の未追跡ファイル由来のみであることを確認し、新規混入ゼロを示す。
3. **frontmatter とリンクの整合** — `version: 6` になっていること、`references/verification-points.md` への相対リンクが実在すること。
4. **配布経路の確認** — `deploy-ai-config` でデプロイ後、`~/.claude/skills/dev-workflow/SKILL.md` の version が 6 になり、`references/verification-points.md` が存在することを確認する（v5 の取りこぼしの再発防止）。
5. **実効性** — スキルは「読まれて効く」ものなので、次回 dev-workflow を起動した実タスクでの遵守が最終的な検証になる。これは即座には確認できないため **未消化として明示** する（新ルール「どれも取れない場合は未検証であることを明示する」の実践）。

## リスクと次サイクルの評価軸

- **references の実効性**: 参照先は「読みに行かれて初めて効く」。本文からのリンク 1 行で十分な誘導になるかは不明。次サイクルで「スタブハーネス方式が実際に使われたか」を observations で確認し、使われていなければ本文へ引き上げるか削る。
- **汎用性**: パターン B の手法は WezTerm / Lua という特定文脈から抽出した。抽象度を上げて書いたが、他言語・他領域で空振りする可能性がある。
- **分量**: SKILL.md は +3.0KB。`hook-scaffold`（9.2KB）と `svleague-match-review`（11.3KB）に次ぐ規模になった。
- **測定**: 次回の evaluate では partial 率だけでなく **「実機確認 / 手動確認が未消化のまま完了」の件数** を指標に加える。直近 14 件中 5 件が該当しており、partial 率（1/14）より実態をよく表す。デプロイ済みかの確認も毎サイクルに含める。
