# ADR-0001: Record architecture decisions

- Status: Accepted (2026-09-12)

## Context

設計判断の根拠がリポジトリの外か、実装手順の文書の中に埋もれている。

GitHub issue のコメントは一次的な置き場としては機能するが、issue を閉じると視界から消え、リポジトリを clone しただけでは読めない。`docs/plan/**` は `.claude/rules/plan-docs.md` の骨格（`## Background` → `## Current structure` → `## Design policy` → `## Implementation steps` → …）が示すとおり実装手順の記録で、決定だけを引く構造になっていない。

骨格が決定を受け止めきれていない実例がすでにある。`docs/plan/2026-08-15_pipeline-effect-metrics.md` は骨格外の `## Decisions` を足し、`docs/plan/2026-07-06_test-changed-repo-scoped-stop-hook.md` は `### 3 案の比較` と `### 推奨案の設計判断` を足している。どちらも「決定とその代替案」を書く場所が無かったために生えたセクションで、plan の他の節に埋もれて検索できない。

結果として、半年後に「なぜこうなっているか」を問われると、issue とコミット履歴と plan を横断して再調査することになる。調査コストが高いだけでなく、再調査の結果として当時と違う結論に達し、決定が静かに揺れる。

## Options considered

| 案                                | 評価                                                                                                                                                                                                                                |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `docs/plan/**` に決定も書き続ける | 新しい仕組みが増えない。ただし plan は実装後に歴史になる文書で、現行の決定と役割が違う。`## Decisions` を骨格に足しても、1 つの plan に複数の決定が混ざる構造は変わらず、決定単位で参照・supersede できない                         |
| issue のコメントに残す            | 追加コストがゼロ。ただしリポジトリ外にあり、clone しただけでは読めず、閉じた issue は検索から外れやすい。エージェントが文脈として自動で読む対象にもならない                                                                         |
| ADR を `docs/adr/` に新設する     | 決定 1 件 = ファイル 1 つになり、番号で相互参照・supersede できる。Nygard 形式というデファクトがあり、書き方を再発明しなくて済む。ファイルが増えるコストはあるが、既存の markdownlint / prettier がそのまま効くので仕組みは増えない |

## Decision

`docs/adr/` に Nygard 形式の ADR を置く。運用ルールは `.claude/rules/adr.md` に 1 本化し、書式の定義はそこだけに持つ。

`docs/plan/**` との棲み分けを次のとおり定める。plan は how を書き、実装が終われば歴史になる。ADR は why を書き、supersede されるまで現行の規範であり続ける。同じ内容を両方に書かず、相互にリンクする。

ADR を書く基準は、後から why を再導出できない決定に限る。

- 選択肢が複数あって片方を選んだ
- 既存の慣習から意図的に逸脱した
- 外部の制約を受け入れて妥協した

逆に、自明な選択、実装手順、一度きりの作業ログは書かない。全部を ADR にすると読まれなくなり、書く側も続かない。

運用を軽く保つため、次の 3 つは意図的に持たない。

- **索引** — ファイル名が連番とタイトルを兼ね、Status は各ファイルの 2 行目にある。手動インデックスは更新が漏れて必ず腐る。
- **テンプレートファイル** — 骨格は `.claude/rules/adr.md` が唯一の定義とし、この ADR 自体が実例を兼ねる。`docs/adr/template.md` を置くと同じ骨格が 2 か所に書かれ、`.claude/rules/code-design.md` の「同時に変更される同一の事実を複数箇所へ直接書かない」に反する。
- **`Proposed` ステータス** — 単一のメンテナしかいないリポジトリでは、提案と受理の間に承認プロセスが無い。`Accepted` / `Superseded by` / `Deprecated` の 3 値で足りる。

## Consequences

決定を覆すときは既存の ADR を書き換えず、新しい ADR を足して古い方の Status を `Superseded by ADR-NNNN` に変える。ADR は編集履歴ではなく決定の系譜として読めるようになるが、「最新の結論」を知るには系譜の末尾まで辿る必要がある。

連番は並行ブランチで衝突しうる。個人リポジトリで並行 PR は稀なので採番の仕組みは作らず、衝突したら後発をリネームする。

lint と format は追加不要で回る。`mise run lint:format` が `markdownlint-cli2 "**/*.md"` と `prettier --check .` を実行し、`.markdownlint-cli2.yaml` の `ignores` に `docs/adr/**` を除外する記述が無いため、新しいファイルは最初から両方の対象になる。

`.claude/rules/adr.md` は `paths: ["docs/adr/**"]` の path-scoped rule なので、`docs/adr/` 配下を編集するエージェントにだけ自動で読み込まれる。書式を守らせるために別途プロンプトへ書き足す必要はない。
