# ADR-0010: Scan Go dependencies with both Dependabot and govulncheck, and defer gosec

- Status: Accepted (2026-10-11)

## Context

`scripts/` 配下の Go モジュール 6 本（agent-stats / ai-bridge / config-diff / nvim-sync / pipeline-metrics / scaffold）について、既知脆弱性の検知が次の状態だった。

- Dependabot の gomod 対象が `scripts/ai-bridge` だけで、残り 5 本は security alert も更新 PR も来ない。
- CI に脆弱性チェックが無い。golangci-lint（`.golangci.yml`）はバグ検出と規約の linter だけで、脆弱性データベースは参照しない。
- 自分のコードの危険な書き方を見る SAST（gosec）も有効化していない。

依存の脆弱性を見る手段として、Dependabot と govulncheck は一見役割が重なる。gosec は golangci-lint に同梱されていて、有効化は 1 行で済む。どれを採るかを決める必要があった。

## Options considered

| 案                                                    | 評価                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dependabot だけ（全モジュールへ拡大）                 | 常時監視と更新 PR は得られる。ただし `go.mod` の版で判定するので、実際に呼んでいない脆弱性でも同じ重さで警告が出る。Go 本体（標準ライブラリ）の脆弱性は対象外。PR で新たに脆弱な関数を呼び始めても、依存の版が変わらなければ反応しない                                                                                                                              |
| govulncheck だけ                                      | 呼び出しグラフで到達性を判定し、標準ライブラリも見る。ただし実行は CI の PR 時だけで、触っていないモジュールに新しい advisory が出ても気付けない。更新 PR も作らない                                                                                                                                                                                                |
| govulncheck を golangci-lint / `<module>:lint` に統合 | golangci-lint に govulncheck 相当の linter は無い。`<module>:lint` タスクに足す場合、lint が脆弱性データベースへのネットワーク依存を持つ。Stop hook（`lint-changed.sh`）が遅くなり、オフラインだと落ちる。advisory の公開でコードが同じでも結果が変わるので、PR の差分と無関係な理由で lint が赤くなる                                                              |
| gosec を有効化                                        | 2026-10-11 に全 6 モジュールで試した。指摘は 53 件で、すべて誤検知だった。内訳は、パーミッション（G301/G302/G306）36 件、変数パスのファイル読込（G304）14 件、変数を使ったサブプロセス起動（G204）6 件、`math/rand`（G404）1 件。G204 は起動するコマンドが固定リストに限られ、引数もシェルを通さず渡す。G404 は一時ファイル名の衝突回避で、セキュリティ用途ではない |

## Decision

Dependabot と govulncheck を併用し、gosec は見送る。

- Dependabot の gomod を `directories: ["/scripts/*"]` にして全モジュールを対象にする。常時の監視と、修正手段（更新 PR）の提示を担う。
- govulncheck を `mise.toml` の `[tools]` に固定し、`ci-go-module.yml` の独立した `vuln` ジョブで実行する。マージ時の門番として、到達可能な脆弱性と標準ライブラリの脆弱性を担う。lint ジョブとは分け、失敗の原因が lint か脆弱性かを区別できるようにする。

gosec を見送る決め手は、このリポジトリの Go が手元で動く CLI だけで、攻撃者が入力を制御できる経路がほぼ無いこと。gosec が効くのは外部入力を受けるサーバや権限境界をまたぐ処理で、現状のコードでは誤検知の抑制作業にしかならない。

## Consequences

依存に関する警告は 2 系統で届く。Dependabot の警告のうち govulncheck が「呼んでいない」と判定したものは、急ぎではないと判断できる。

govulncheck は各モジュールの `on.pull_request.paths` に一致する PR でしか走らない。そのため、標準ライブラリに新しい脆弱性が出ても、そのモジュールを次に触るまで気付けない。この隙間は受け入れる。気になった時点で、`ci-go-module.yml` の呼び出し元に `schedule` を足す。

gosec は次の条件で見直す。

- Go で外部入力を受けるもの（Webhook の受け口、HTTP サーバなど）を追加したとき。
- 既存 CLI が、他人が書いた入力（共有リポジトリの設定、ネットワーク越しのデータ）を解釈するようになったとき。

その場合は G301/G302/G304/G306 を除外して有効化し、残った指摘には安全である理由を書いた `//nolint` を付ける形から始める。
