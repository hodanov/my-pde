# Go test rules

Goテストは、自分たちのコードが提供する振る舞いを決定的に検証する。

## テスト対象

- 標準ライブラリやサードパーティライブラリ自体の挙動を再検証しない。
- 値の受け渡しだけを行うコードでは、自コードが設定・変換した結果を直接検証する。
- 実HTTP経路にリクエスト構築、分岐、デコードなどの自コードがある場合だけ `httptest` を使う。
- 公開入口のテストで内部ルールを重複して網羅せず、各規則を所有する関数・メソッドのテストへ寄せる。

## Table-driven tests

- 複数ケースは `name` フィールドを持つstructスライスで定義する。
- 入力フィールドには役割が分かる名前、期待値には `want` または `want*` を使う。
- エラー有無だけを検証する場合は `wantErr bool`、特定のエラーを検証する場合は `wantErrIs error` を使う。
- 同じ関数・メソッドの正常系、異常系、状態遷移は、可能な限り一つのテーブルから見渡せるようにする。
- ケース名は既存ファイルの言語と表現へ揃え、失敗条件または期待する振る舞いを具体的に書く。

## 並列実行

- テスト関数と各サブテストへ `t.Parallel()` を付ける。
- `t.Setenv` を使うテスト関数・サブテストへ `t.Parallel()` を付けない。
- package変数、環境変数、作業ディレクトリなど共有プロセス状態を変更するテストは並列化しない。
- モック、テスト対象、可変なslice・map・clockは各サブテスト内で生成する。

## 返り値の検証

- テスト対象の返り値を、不要な変換を挟まず直接検証する。
- 複数の返り値には、それぞれ対応する `want*` フィールドを持たせる。
- 構造体は、フィールド追加の検証漏れを防ぐため全体比較を優先する。
- 巨大な戻り値や非決定的な値は、契約上意味のある箇所だけを検証する。
- エラーは `errors.Is` または `errors.As` で、対象コードが公開する契約に合わせて検証する。
- エラー文言は、その文言自体が公開契約である場合だけ検証する。
- 比較の都合だけで本番コードへ公開アクセサや `Equal` メソッドを追加しない。

## モック

- 既存のportに生成済みモックがある場合は `go.uber.org/mock` のモックを使う。
- モックの戻り値と呼び出し回数は、可能な限りテーブルのフィールドで表現する。
- 呼び出し順や連続した戻り値など、宣言的なフィールドで表せない差だけを `setupMock` に閉じ込める。
- `setupMock` や `DoAndReturn` の中でアサーションを行わず、観測値を共通ランナーへ返して検証する。
- テスト目的だけのinterfaceや手書きモックを本番コードへ追加しない。

## コールバックと並行処理

- ケース固有の実行手順が必要な場合だけ `exercise` を使い、返り値と観測結果を返す責務に限定する。
- `setupMock`、`exercise`、worker goroutineの中で `t.Fatal`、`t.FailNow`、アサーションを呼ばない。
- goroutineの結果はchannelなどで回収し、テストを実行するgoroutineで検証する。
- 同期はbarrierやchannelで決定的に行い、`time.Sleep` やスケジューリングへ依存しない。
- goroutine、同期プリミティブ、共有状態を扱うテストを変更したら、対象packageへ `go test -race` を実行する。

## テストヘルパ

1. 一つのテスト関数だけで使う型・関数は、そのテスト関数内へ置く。
2. 同一packageの複数テストで共有するヘルパは、専用の `_test.go` ファイルへunexportedで置く。
3. 複数packageで共有する必要が明確な場合だけ、`internal/testutil` へ置く。

`*testing.T` を受け取るヘルパでは先頭で `t.Helper()` を呼ぶ。

## リソース管理

- request body、response body、ファイルなどテストが所有するリソースは、各サブテスト内で解放する。
- 消費・変更される値をケース間で共有せず、必要ならケースごとのfactoryから生成する。
- `errors.Join` の結果は、非nil要素がないと `nil` になることを前提に検証する。
